# Main-part semantic permutation graph

`sm-shaders main-part-graph` converts every recovered `main_part` pixel
permutation into a selector-independent semantic descriptor. The descriptor
records the output contract, material, texture sources, normal and coverage
policies, lighting, reflection, refraction, composition, and remaining feature
flags.

```powershell
uv run sm-shaders main-part-graph output `
  --output output/reports/main-part-permutation-graph.json

uv run sm-shaders main-part-graph output --summary-only

uv run sm-shaders main-part-families output `
  --output output/reports/main-part-family-candidates.json

uv run sm-shaders main-part-synthesis output `
  --output output/reports/main-part-synthesis.json `
  --spec-dir output/reports/main-part-synthesis-specs
```

The graph has three deliberately separate concepts:

1. A **requirement** is a semantic choice such as
   `lighting.transmission` or `coverage.dissolve_uv1`.
2. A **phase implementation** is a typed HLSL symbol and its owning reusable
   asset. Registry entries never contain selector hashes.
3. A **graph template** will wire compatible implementations into a typed
   entry point. A permutation is not safe to migrate merely because every
   individual phase exists; their data contracts and ordering must also have a
   validated template.

The initial report therefore distinguishes missing phases from
`instruction_ordered_uncomposed_count`. The latter is the high-leverage queue:
those shaders already have reusable ingredients and need a shared graph
adapter, not another recovered algorithm.

## Skeleton clustering

The report groups instruction-ordered shaders by a semantic skeleton that
removes only quality and reflection policy. A single skeleton can therefore
show the complete low/medium/high and off/single/multi matrix. Implementing and
validating one graph template can migrate the whole group.

The intended workflow is:

1. Select the largest phase-complete skeleton.
2. Recover typed structs for the values crossing its phase boundaries.
3. Add a graph template that wires existing registry symbols.
4. Compile and reflect every matching permutation.
5. Run active-path GPU differential fuzzing per distinct policy combination.
6. Install every validated member and regenerate the graph report.

Missing-phase counts drive a different workflow: implement the highest-impact
typed phase once, register it, and observe which skeletons become complete.

## Family compiler

`main-part-families` is the batch-planning front end. It canonicalizes entry
interfaces and decompiler register-state names, removes quality and reflection
from the family identity, and mines the remaining instruction-ordered shaders
into complete policy matrices. Each candidate contains:

- the selector-independent semantic skeleton;
- the recovered input/output contract;
- observed and missing quality × reflection combinations;
- cross-permutation common-token coverage and the number of shared and
  policy-divergent instruction regions;
- the transitive reusable-asset set;
- activation fixtures required by its phase contracts; and
- a generated graph-specification draft.

The current corpus produces 92 multi-member candidates covering 382 shaders;
82 are complete policy matrices. This changes the planning unit from one
selector to one graph specification, commonly unlocking nine shaders at once.
The body alignment score also prevents a large define matrix from being ranked
as an easy extraction when its recovered programs share little mechanical
structure.

The first miner-selected family has now completed that workflow. Nine tinted
UV1-dissolve glass permutations became one typed evaluator with explicit
default/medium/high and off/single/multi axes. Their wrappers are ABI-compatible
and a 128-case campaign per member compared 9,216 GPU output values bit-exactly.
The structural inventory increased from 181 to 190 shaders, and the completed
family disappeared from the candidate queue. The next candidate is another
nine-member matrix with 45% common-token coverage.

Graph entry wrappers are generated by `main_part_graph_codegen.py` from policy
axes, semantic bindings, and conditional ABI include rules. The directional
glass template is the first existing family migrated to this generator, so the
new architecture is already on the production lifting path rather than being
report-only infrastructure.

`main-part-synthesis` is the compiler-induction layer above the miner. It
lowers recovered entry bodies to dependency-aware normalized operations,
anti-unifies every member of a family, and emits policy holes with typed live
inputs and outputs, runtime resources, side effects, controlling axes, and
matches into the semantic phase registry. Its readiness categories separate
families that can be generated automatically from those needing another typed
phase contract or a human semantic partition.

On the current corpus, the pass classifies 41 families containing 209 shaders
as `auto_with_typed_residuals` and writes one semantic-named graph
specification per family. None are mislabeled `auto_composable` while residual
implementations remain. Another 29 families need semantic partitioning and 22
are currently irregular. All global phase contracts used by these families
have typed ports; the remaining 1,000 unmatched policy regions are explicitly
recorded as family-local residuals instead of being hidden in anonymous include
files.

The generated specifications are compiler inputs, not claims that the shaders
have already been installed. The emission backend turns each residual into a
real typed HLSL helper, composes the shared skeleton, then compiles, reflects,
fuzzes, and installs the family as one transaction. Helper signatures carry
the region's live entry parameters and explicit `inout` state. Filenames and
helper symbols are derived
from the full semantic skeleton and entry interface. Selector IDs and content
hashes are forbidden as naming fallbacks, and collisions fail the campaign.

`main-part-synthesis-emit` is that source-preserving backend. It aligns complete
top-level statements and control blocks rather than arbitrary token fragments,
emits common regions once, and emits policy-dependent statements as typed
family-local helper functions. Generated policy macros are not used. The
resulting selector snippets retain only their ABI,
one policy coordinate, one semantic include, and an evaluator call. `--apply`
is transactional: the recipe asset, installed asset, every member wrapper, and
the manifest are rolled back byte-for-byte if compilation, reflection, or any
GPU differential case fails.

The first emitted family is
`transparent_surface_water_tangent_map_dissolve_uv0_fog_cutoff`: nine shaders
now share one evaluator with nine common regions and ten complete policy
regions. All nine passed 64 active GPU cases at zero tolerance before the
transaction committed.

## Validated templates

The compiler currently admits three transparent-surface templates:

- `transparent_glass_surface` composes the recovered texture, normal,
  dissolve/cutout, clustered-light, reflection, and frame-composition phases.
- `directional_glass_surface` replaces only the material frontend with the
  FBDRF directional-map policy. Its default, medium, and high quality variants
  share one entry evaluator and select off/single/multi reflection at compile
  time. High quality adds two isolated phases: typed cascade/cloud visibility
  and mip-aware indirect/frame composition. Cluster traversal and reflection
  remain the same implementations used by medium quality.
- `tinted_dissolve_glass_surface` shares UV1 dissolve material decoding and
  tinted composition across a complete 3 x 3 matrix. Medium and high policies
  activate clustered lights; high additionally activates cascade/cloud
  visibility, opaque-depth refraction, indirect light, and mip-aware frame
  composition.

The nine directional-glass members are ABI validated as one graph. GPU
differential campaigns cover all three high reflection policies; clustered
fixtures use populated point/spot/probe masks for both medium and high quality.
